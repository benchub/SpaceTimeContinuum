# Space Time Continuum — Client/Server Protocol

**Protocol version: 1**

This document is the single source of truth for communication between the Space Time
Continuum app (this repo) and the leaderboard server (private repo
`SpaceTimeContinuumServer`). Any change to either side must be reflected here first.

## Basics

- Base URL: `https://spacetime.silentmedia.com`
- All bodies are JSON (`Content-Type: application/json; charset=utf-8`).
- All timestamps are integer **UTC Unix epoch seconds**.
- All distances are **meters** (floating point), all durations are **seconds** (integers).
- `:guid` is a lowercase RFC 4122 UUID string generated by the app on first launch
  (and regenerated when the user resets their history).
- `:name` is percent-encoded in the path.

### Request headers

| Header | Required | Value |
|---|---|---|
| `X-STC-Protocol` | yes (except `GET /units`) | `1` |
| `X-STC-Token` | on `/sample`, `/name` | Per-device secret: 64 hex chars (32 random bytes) generated alongside the GUID. Never displayed to the user. |
| `User-Agent` | yes | `SpaceTimeContinuum/<app version> (<os name> <os version>)` (presence is required; format is informational) |

### Device identity (trust on first use)

There is no explicit registration call. The first authenticated request (`/sample` or
`/name`) for an unknown GUID creates the device and stores a digest (SHA-256) of the
supplied `X-STC-Token`. All later authenticated requests for that GUID must present the
same token, otherwise the server answers `401`.

When the user resets their history, the app generates a **new GUID and token**. The old
device is abandoned on the server (its name stays reserved; the server may garbage-collect
abandoned devices).

### Error envelope

Any non-2xx response has the body:

```json
{ "status": "error", "message": "human readable explanation" }
```

| Code | Meaning |
|---|---|
| 400 | Malformed request (bad JSON, bad GUID, bad name syntax) |
| 401 | Token missing or does not match the device |
| 409 | Conflict (name unavailable — see `/name`) |
| 413 | Too many samples in one request |
| 429 | Rate limited. `Retry-After` header (seconds) is set. Limits are server-defined and may change. |
| 5xx | Server problem. Client retries later. |

## Endpoints

### `POST /sample/:guid` — upload minute rollups

Sent only when the leaderboard is enabled **and** the computer is unlocked, every
5 minutes ± 30 s (uniform random jitter). Contains every row with `uploaded_at IS NULL`,
oldest first, at most **1440** per request. If more remain, the client sends the next
batch immediately after a success.

When a user first joins the leaderboard, their entire local history is uploaded (in
batches) — history before joining is included.

Request:

```json
{
  "utc_offset_s": -25200,
  "samples": [
    {
      "minute_start": 1760365200,
      "screen_on_s": 60,
      "unlocked_s": 60,
      "attentive_s": 60,
      "key_active_s": 12,
      "key_presses": 41,
      "key_distance_m": 0.0451,
      "pointer_active_s": 20,
      "pointer_distance_m": 1.274,
      "any_active_s": 25
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `utc_offset_s` | Device's current offset from UTC (informational). |
| `minute_start` | Start of the minute, multiple of 60. |
| `screen_on_s` | Seconds (0–60) during which at least one display was awake. |
| `unlocked_s` | Seconds (0–60) during which the session was unlocked and on console. |
| `attentive_s` | Seconds (0–60) that were both screen-on and unlocked. |
| `key_active_s` | Seconds (0–60) containing ≥1 key press. |
| `key_presses` | Number of key presses (key-down, excluding auto-repeat). |
| `key_distance_m` | Sum of key travel for those presses. |
| `pointer_active_s` | Seconds (0–60) containing pointer movement. |
| `pointer_distance_m` | Physical on-screen distance the pointer travelled. |
| `any_active_s` | Seconds (0–60) containing key presses **or** pointer movement. |

A sample whose `minute_start` is missing or not an integer makes the whole request fail
with `400`, since it couldn't be reported in `rejected`.

Server validation for each sample (if it fails, the sample is *rejected*, not the request):

- `minute_start % 60 == 0`, `>= 1704067200` (2024-01-01), `<= now + 120`
- all `*_s` fields in `0...60`; `attentive_s <= min(screen_on_s, unlocked_s)`;
  `any_active_s >= max(key_active_s, pointer_active_s)`; `any_active_s <= key_active_s + pointer_active_s`
- `0 <= key_presses <= 1200` (20/s), `0 <= key_distance_m <= 12.0`
- `0 <= pointer_distance_m <= 300.0`

Response `200`:

```json
{
  "status": "ok",
  "accepted": [1760365200],
  "rejected": [ { "minute_start": 1760365260, "reason": "key_presses out of range" } ]
}
```

- Re-uploading an already stored `minute_start` is **idempotent**: it is reported as
  accepted and the stored row is left unchanged.
- The client sets `uploaded_at = now` for every `minute_start` in **both** `accepted` and
  `rejected` (rejections are permanent; retrying would never succeed).
- Any non-200 response: nothing is marked; retry on the next cycle (honor `Retry-After`).

### `GET /check/:guid/:name` — is a leaderboard name available?

The client debounces: at most one request per second, only the most recent typed value is
sent, and responses for stale values are ignored. No token required.

Response `200`:

```json
{ "name": "SpaceCadet", "available": true }
```

```json
{ "name": "SpaceCadet", "available": false, "reason": "taken" }
```

`reason` is one of `taken`, `invalid`, `reserved`. A name already owned by `:guid` is
reported `available: true`.

**Name rules:** 3–50 characters; letters, digits, space, `_`, `-`, `.`; must start and
end with a letter or digit; uniqueness is case-insensitive. Leading/trailing whitespace
is trimmed by the client before sending.

### `POST /name/:guid/:name` — claim a leaderboard name

Requires `X-STC-Token`. Empty body.

| Code | Body | Meaning |
|---|---|---|
| 200 | `{ "status": "success", "name": "SpaceCadet" }` | Name is now owned by this GUID (any previous name is released). |
| 409 | `{ "status": "unavailable", "name": "SpaceCadet" }` | Someone else owns it (possibly just won a race), or the name is reserved. |
| 4xx/5xx | `{ "status": "error", "message": "..." }` | Anything else (invalid syntax, auth, server error). |

### `GET /units` — New Entropy silly units

No authentication. Supports `ETag`/`If-None-Match` (`304 Not Modified`). The client
checks at most once per day when New Entropy is enabled. Format: see
[units-format.md](units-format.md). A response that fails validation is ignored and the
client keeps its current list.

### `GET /quips` — New Entropy stretch reminders

No authentication. Same caching behaviour as `/units`. Body:
`{"stretch": ["Stand up and reach for the ceiling.", ...]}`. Quips are trimmed, at most 200
characters, and duplicates are ignored; a response with no valid quips is ignored. The
app mixes them in with its built-in stretch reminders and shows each one before repeating
any. Source: [`shared/quips.json`](../shared/quips.json).

## Server-side presentation (informational)

The public leaderboard (HTML, not part of the app protocol) ranks devices that have a
name by keyboard distance, pointer distance and active time (`any_active_s`) over
**today**, **this week** (Monday-start) and **all time**, using UTC day boundaries. A
map shows named devices at the approximate location of their most recent IP address
(city-level geolocation, possibly wrong). Devices that haven't uploaded for 2 months are
hidden from the leaderboard and map until they upload again; their data is kept.
